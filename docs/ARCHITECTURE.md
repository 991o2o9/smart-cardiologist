# Архитектура Smart Cardiologist 🏗️

## Обзор

Smart Cardiologist - это микросервисное приложение, построенное на FastAPI с использованием современных практик разработки. Проект следует принципам чистой архитектуры и разделения ответственности.

## Структура проекта

```
smart-cardiologist/
├── src/                    # Исходный код
│   ├── api/               # API роутеры (контроллеры)
│   ├── models/            # Pydantic схемы (DTO)
│   ├── services/          # Бизнес-логика (сервисы)
│   ├── utils/             # Утилиты и вспомогательные функции
│   └── main.py           # Точка входа приложения
├── tests/                 # Тесты
│   ├── unit/             # Unit тесты
│   └── integration/      # Integration тесты
├── config/               # Конфигурация
├── scripts/              # Скрипты управления
├── data/                 # Данные
└── docs/                 # Документация
```

## Слои архитектуры

### 1. API Layer (src/api/)
**Ответственность:** Обработка HTTP запросов, валидация входных данных, маршрутизация.

**Компоненты:**
- `cardio_assistant.py` - API для кардио-ассистента
- `heart_prediction.py` - API для предсказания риска

**Принципы:**
- Только обработка HTTP запросов
- Делегирование бизнес-логики сервисам
- Валидация через Pydantic схемы

### 2. Models Layer (src/models/)
**Ответственность:** Определение структур данных и схем валидации.

**Компоненты:**
- `schemas.py` - Pydantic модели для API

**Принципы:**
- Строгая типизация
- Автоматическая валидация
- Документация API

### 3. Services Layer (src/services/)
**Ответственность:** Бизнес-логика, интеграция с внешними сервисами.

**Компоненты:**
- `ai_service.py` - Сервис для работы с Groq AI
- `ml_service.py` - Сервис для работы с ML моделью

**Принципы:**
- Инкапсуляция бизнес-логики
- Независимость от API слоя
- Легкое тестирование

### 4. Utils Layer (src/utils/)
**Ответственность:** Переиспользуемые утилиты и инфраструктурные компоненты.

**Компоненты:**
- `cache.py` - In-memory кеш с TTL
- `rate_limiter.py` - Ограничение запросов

**Принципы:**
- Переиспользуемость
- Простота использования
- Высокая производительность

## Паттерны проектирования

### 1. Dependency Injection
Сервисы инжектируются в API роутеры, что обеспечивает:
- Слабое связывание компонентов
- Легкое тестирование
- Гибкость конфигурации

### 2. Repository Pattern
ML сервис инкапсулирует работу с моделью:
- Абстракция доступа к данным
- Легкая замена реализации
- Централизованное управление состоянием

### 3. Factory Pattern
Создание сервисов через фабрики:
- Контролируемое создание объектов
- Конфигурируемые зависимости
- Управление жизненным циклом

### 4. Strategy Pattern
Различные стратегии кеширования и rate limiting:
- Плагинная архитектура
- Легкое расширение функциональности
- Конфигурируемое поведение

## Принципы SOLID

### Single Responsibility Principle (SRP)
Каждый класс имеет одну ответственность:
- API роутеры - только обработка HTTP
- Сервисы - только бизнес-логика
- Утилиты - только вспомогательные функции

### Open/Closed Principle (OCP)
Система открыта для расширения, закрыта для модификации:
- Новые API endpoints через роутеры
- Новые сервисы через интерфейсы
- Новые утилиты через абстракции

### Liskov Substitution Principle (LSP)
Подклассы могут заменять базовые классы:
- Интерфейсы сервисов
- Абстрактные классы утилит
- Полиморфные компоненты

### Interface Segregation Principle (ISP)
Клиенты не зависят от неиспользуемых интерфейсов:
- Минимальные интерфейсы
- Специализированные контракты
- Четкое разделение ответственности

### Dependency Inversion Principle (DIP)
Зависимости от абстракций, а не от конкретных реализаций:
- Инверсия зависимостей
- Слабое связывание
- Тестируемость
